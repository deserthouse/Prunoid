## 0. 一句话结论

**项目可行，且存在明确的市场空缺**：基于 root 的「SDK 知识库驱动 + 组件级禁用 + 安装/更新自动重应用」工具目前**没有任何一个现存项目同时做到这三点**。技术路线以 **IFW（Intent Firewall）为主、pm disable 为辅**，数据冷启动可合并 5 个开源数据源，知识库可完全自建并社区共建。建议立项。

## 2. 技术路线调研

### 2.1 组件禁用三种手段对比

| 手段 | 权限要求 | 对 app 可见性 | 持久性 | 备注 |
|---|---|---|---|---|
| **pm disable**（root） | root | ⚠️ **app 可查询自身组件状态，也可在运行时自行恢复启用** | 写入 `/data/system/users/0/package-restrictions.xml`（Android 12+ 为 ABX 二进制格式），**跨 app 更新保留**，卸载重装后重置 | Blocker/AppManager/XDA 脚本均支持；老牌方案 |
| **IFW 意图防火墙**（root） | root（写 `/data/system/ifw/*.xml`） | ✅ **组件在 app 看来仍是 enabled，但无法启动**——对抗检测的最优解 | 规则文件持久，AppManager 实测"app 无法自行解除" | Android 4.4.2 至 **Android 16 实测仍有效**（2025-07 JTech 论坛 + Magisk 模块验证）；**已知缺陷：component-filter 规则不拦截隐式广播**（如 BOOT_COMPLETED），需 intent-filter 规则补充（Blocker issue #1050） |
| **Shizuku（ADB 激活）** | 无 root | 同 pm disable | 同 pm disable | ❌ **shell 权限无法禁用普通应用的组件**（AOSP 限制，仅 test-only APK 例外）——Blocker 官方 FAQ 明确确认。**结论：Shizuku 仅在以 root 启动时可用，不能作为无 root 主渠道** |

### 2.2 关键机制验证

- **pm disable 跨更新保留**：组件禁用状态按"包名/组件名"键存储，应用升级（update）后保留；但**更新可能引入新组件**（新版 SDK 新增 receiver 等），所以仍需要"更新后重扫描重应用"——这正好是需求②的价值点。卸载重装则完全重置，由 `PACKAGE_ADDED` 广播兜底。
- **app 自恢复对抗**：应用有权调用 `setComponentEnabledSetting` 重新启用自己的组件，pm disable 可能被运行时"翻案"；**IFW 在框架层拦截启动，app 无感知也无法绕过**（只能感知"启动失败"）。因此推荐 **IFW 为主、pm disable 为辅** 的双引擎。
- **误禁系统组件风险**：真实案例（AppManager GitHub issue）显示错误禁用可致 bootloop，恢复需进 recovery 删 `/data/system/ifw/` 下的规则文件 + 编辑 package-restrictions.xml。**必须有系统组件白名单 + 安全模式（检测到 bootloop 前 N 次启动失败自动清规则）机制**——参考 AppManager 的恢复文档设计。
- **免 hook 的检测规避原理成立**：不注入目标进程、不改 APK、不 hook 任何 Java 方法，反 hook 检测（HookDetection、RootBeer、Xposed 检测等）不适用；IFW 模式下连组件状态都不改变，检测面最小。注意：root 本身的痕迹（Magisk）是另一回事，由用户自行处理（如 Shamiko）。

### 2.3 先例工程验证（此路有人走通过）

- **XDA "Disable Tracking Services" 脚本**：从 Exodus Privacy 下载 tracker 名单 → `pm disable` 所有匹配组件。本需求的最小可行原型，社区验证多年。
- **AppManager**（GPL-3.0，7.4k stars）：内置"一键屏蔽广告/追踪组件"，使用 Exodus 签名库扫描 + IFW 禁用，支持 Watt/Blocker 规则导入。
- **Blocker**（MIT，Now in Android 架构，Compose + M3）：PM/IFW 双模式，兼容 MyAndroidTools 备份导入，活跃维护（2026 年仍更新）。
- **AdHammer**（闭源）：dex 逆向确认含 root pm disable + 包安装/更新监听的完整链路。

### 3.2 空缺确认与自建可行性

**结论：目前不存在"面向安全禁用的组件级 SDK 知识库"开源项目**——所有现存项目要么只做识别（LibChecker/Exodus）不做禁用，要么有禁用无知识库（Blocker/MyAndroidTools），要么闭源（AdHammer/MyAndroidTools）。这个空缺真实存在。

**我们有能力自建**，方案（参考 LibChecker-Rules 的成熟模式）：

```
规则条目 = {
  SDK 标识: 名称 + 厂商 + 官网 + 类别(广告/统计/推送/推送联盟/热修复/风控/地图...),
  检测特征: 包名前缀列表 + 类签名(Exodus式) + manifest 特征(intent-action/meta-data),
  组件清单: 各 app 中常见 activity/service/receiver/provider 命名模式,
  处置建议: 禁用安全等级(安全禁用/谨慎禁用/禁用会破坏功能/勿动),
  白名单: 禁用后可能导致崩溃的已知组件,
  来源与置信度: 数据出处 + 实机验证记录
}
```

- **冷启动**：脚本合并 Exodus API + LibChecker-Rules(Apache-2.0) + AdClose 名单 + Thanox 源码名单 + GKD 知识，人工审核安全等级 → 预计首版 100~150 个 SDK。
- **共建**：GitHub 仓库 + PR 模板 + CI 自动校验（schema 校验 + 规则冲突检测，照搬 ETIP/LibChecker 的机制）。
- **端侧消费**：app 内规则订阅（支持自建源 URL），规则带版本号做增量更新。

## 5. 风险矩阵

| 风险 | 等级 | 说明 | 缓解措施 |
|---|---|---|---|
| 误禁系统组件致 bootloop | 🔴 高 | 有真实案例 | 内置系统包白名单；首版明确不支持系统 app；提供"安全模式"恢复（桌面快捷方式一键清除全部 IFW 规则 + recovery 教程）；操作前强制导出备份 |

## 6. 建议产品架构（草案，待拍板）

```
SDK-Slayer
├── 端侧 App（Kotlin + Compose + M3，参考 Blocker 的 NiA 架构；libsu/librootkotlinx 做 root）
│   ├── 扫描器：解析目标 app manifest（包名前缀 + Exodus 式类签名 + LibChecker 组件规则）→ SDK 识别报告
│   ├── 禁用引擎：IFW 主引擎（写 /data/system/ifw/）+ pm disable 辅引擎（root shell / root-Shizuku）
│   ├── 规则订阅：知识库版本化拉取 + 本地缓存 + 自定义源
│   ├── 自动化（进阶）：PACKAGE_ADDED/REPLACED 监听 → 后台重扫描 → 增量重应用规则
│   └── 安全层：系统白名单 / 一键恢复 / 规则备份导出
└── 规则仓库（独立 GitHub repo，Apache-2.0，PR + CI 校验共建）
```

**分阶段路线建议**：
- **M1（最小可用）**：扫描 + 识别 + 手动一键禁用（IFW）+ 内置规则快照 + 备份/恢复
- **M2**：规则订阅更新 + pm/IFW 双引擎切换 + 安全等级提示细化
- **M3（进阶）**：安装/更新自动处理 + Magisk 模块模式 + 社区共建流程上线

## A. Thanox v8.6（github.tornaco.android.thanos，2025-10-01 发布）

### A1. 资料来源完全挖清（回答"挖到资料来源"的目标）

Thanox 的 SDK 知识来自**两套内置数据**：

**① `assets/blocker_rules/{en,zh_CN}/general.json` —— 468 条组件禁用规则**（中英双语两份），单条结构：

```json
{"id":1, "name":"穿山甲广告SDK", "company":"北京巨量引擎网络技术有限公司",
 "searchKeyword":["com.ss.android.socialbase.","com.bytedance.sdk.openadsdk.", ...],
 "useRegexSearch":false, "description":"...",
 "safeToBlock":true, "sideEffect":"未知", "contributors":["溯澜染汐"]}
```

统计：
- 总 468 条，其中 **418 条贡献者标注为 "Exodus Tracker Investigation Platform"**（程序化从 Exodus ETIP 转化）、50 条来自社区个人贡献者（溯澜染汐 35、Mercury 12 等）
- **仅 39 条标记 safeToBlock=true，429 条标记为不可安全禁用**——"哪些能安全禁"的数据极度稀缺，印证本项目知识库的价值空间
- **没有已知独立上游仓库**：该 JSON 直接打包在 APK 内，社区贡献走应用内提交，GitHub 上无独立规则 repo（代码搜索无 safeToBlock 独立项目）——**这套数据被锁死在 Thanox 里，无人独立维护**，正是我们的机会

**② `assets/lcrules/rules.db` —— SQLite 库，2204 条组件级识别规则**（"LC"即 LibChecker，Thanox 集成了 LibChecker 系规则）：

| type | 数量 | 含义 | 示例 |
|---|---|---|---|
| 0 | 1247 | 原生库 so | libxguardian.so→信鸽推送、libmarsxlog.so→Mars |
| 2 | 380 | Activity | com.qq.e.ads.RewardvideoLandscapeADActivity→腾讯广告SDK |
| 1 | 243 | Service | com.xiaomi.mipush.sdk.MessageHandleService→MiPush |
| 3 | 113 | Receiver | com.igexin.sdk.FlymePushReceiver→个推代管魅族推送 |
| 4 | 138 | Provider | com.sensorsdata...SensorsDataContentProvider→神策分析 |
| 5 | 82 | 静态库包名 | androidx.lifecycle→Jetpack Lifecycle |

这套库覆盖国内 SDK 的组件全类名 + 中文标注（信鸽/米大师/神策/Pangle/各厂商推送...），**是我们规则库冷启动可以直接对标的数据形态**。

### A2. 对本项目的直接影响

1. **规则 Schema 已有现成范本**：Thanox 的 general.json 字段（name/company/searchKeyword/safeToBlock/sideEffect/contributors）与调研报告 §3.2 提议的规则条目几乎一致——证明该 schema 是社区实践收敛出的形态，我们照此扩展即可
2. **识别引擎范本**：lcrules 证明"组件全类名 + 类型 + 中文标注"的 SQLite 形态可在端侧高效工作（Thanox 组件屏蔽功能即基于此）
3. **知识库定位确认**：Thanox 把 468 条规则锁在 APK 内、无独立仓库、39/468 的安全标注覆盖率——"社区共建的安全禁用知识库"这个生态位**确实空着**

# 增补二：独立 SDK/追踪器数据库盘点——LibChecker 之外还有什么（2026-09-13 第三轮）

> 问题：除 LibChecker 维护的规则外，是否存在独立的社区共建 SDK 库？是否已被 LibChecker 完整收录？
> 结论：**独立存在多家，但各占不同维度，互不覆盖，LibChecker 谁也没完整收录**。

## D1. 独立数据库全景（按维度分类）

| 数据库 | 维度 | 规模/活跃度 | 协议 | 与 LibChecker 关系 |
|---|---|---|---|---|
| **Exodus Privacy ETIP** | 类签名级（dex 类名签名） | 2024-01 数据：603 个 tracker 在册、574+29 条签名、428+27 个已确认；API 实时更新 | AGPL（平台）| **完全独立**，互不收录。Thanox 的 468 条禁用规则反而证明了"Exodus×组件禁用"的合并价值 |
| **DuckDuckGo tracker-blocklists（app/android-tds.json）** | 网络域名级 + 部分包名（packageNames + owner 实体 + 收集数据类型信号） | 官方自动+人工维护，App Tracking Protection 在用，活跃 | **CC BY-NC-SA 4.0（禁商用）** | 完全独立，维度不同（网络请求 vs 组件/库） |
| **Disconnect / X-Ray / TrackerControl 系** | 网络域名级 | TrackerControl 聚合 Disconnect+X-Ray+DDG，活跃 | 各自不同 | 独立，域名维度 |
| **oF2pks/3xodusprivacy-toolbox**（GitLab） | Exodus 之外的补充 tracker 索引 | "**31 known additions**"（ETIP-standby/missing 分类），配套 ClassyShark3xodus（最后更新 2024-01） | Apache-2.0 | 独立小体量补充源，明确标注 Exodus 漏收的条目 |
| **AppManager 内嵌签名库** | 类签名级 | 编译进 app 源码（submodule），接受社区投稿"ad/tracking signatures" | GPL-3.0（随主项目） | 独立维护但无独立数据仓库，不可整体复用 |
| **LibChecker-Rules** | 组件级 + so 库（四类组件目录） | 2204 条（v40），2026-09 仍活跃 | Apache-2.0 | — |
| **Thanox lcrules/rules.db** | 组件级（从 LibChecker 提炼打包） | 2204 条，随 APK 更新 | 锁在 APK 内 | 是 LibChecker 的下游消费，非独立上游 |
| **Fuck.AD / AdClose hook 名单** | hook 入口类级 | 16+ 厂商，私有云端（fkad.hujiayucc.cn） | 不公开 | 独立，需逆向获取 |

## D2. 关键判断

1. **"组件级 + 开源 + 活跃共建"这个交集里只有 LibChecker-Rules 一家**。Exodus（签名级）、DDG（域名级）、Disconnect（域名级）都是独立且权威的，但维度不同——LibChecker 既没有收录它们，也收录不了（数据形态不同）。
2. **跨库合并层是空白**：没有任何项目做过"Exodus 签名 + LibChecker 组件 + DDG 域名 → 统一 SDK 实体"的对齐合并（Thanox 只做了 Exodus→禁用规则的简单转化）。这正是 SDK-Slayer 规则库的差异化空间：以 SDK 实体为中心，聚合多源特征 + 安全标注。
3. **协议注意**：DDG 名单是 **CC BY-NC-SA（禁商用）**——只能参考学习、不能直接进我们的 Apache-2.0 仓库；Exodus 数据经 API 使用（注意其 AGPL 平台性质，规则事实本身可用）；oF2pks 补充索引 Apache-2.0 可直接用；LibChecker-Rules Apache-2.0 可直接用。

# 增补三：覆盖度实测——Fuck.AD 与 Thanox 规则是否已被 LibChecker 完整收录（2026-09-13 第四轮）

> 方法：克隆 LibChecker-Rules v44 全库（2673 条规则路径），与 Thanox 468 条禁用规则、Thanox 内置 lcrules 2204 条、Fuck.AD 14 家 SDK 做程序化交叉比对。脚本与数据存 `research/`。

## E1. 比对结果（三组量化数据）

**① Thanox 468 条禁用规则 → LibChecker 覆盖率：6%**

| 覆盖情况 | 条数 | 占比 |
|---|---|---|
| 关键词全覆盖 | 31 | 6.6% |
| 部分覆盖 | 18 | 3.8% |
| **零覆盖** | **419** | **89.5%** |

零覆盖的大头是 Exodus 转化的欧美追踪 SDK（Flurry/AppsFlyer/Braze/mParticle/MoPub/Localytics/Weborama/SmartAdServer...）**以及中文推送/广告 SDK（极光推送、小米推送、魅族/vivo/OPPO 推送、B站广告、京东CPS、百度小游戏广告等）**——LibChecker 的组件级规则完全没有这些包的前缀。原因：Exodus 规则是签名级（任意类名签名），LibChecker 只收"可作为组件/库识别锚点"的具体类，两者收录逻辑不同。

**② Thanox 内置 lcrules（2204 条）→ LibChecker 当前版覆盖：95.8%**

- 精确匹配 2003 条，未收录仅 87 条——其中 74 条是 type5"静态库包名"（LibChecker v44 已把该类目重组，现归 chart/static 体系），13 条 native so
- 结论：**这部分基本被完整覆盖且 LibChecker v44 更新**（Thanox 用的是 v40 旧快照），直接用上游即可，无需依赖 Thanox 的副本

**③ Fuck.AD 14 家广告 SDK → LibChecker 组件级覆盖：8/14**

| ✅ 已有组件规则（命中数） | ❌ 完全没有 |
|---|---|
| TopOn(12)、百度(8)、优量汇(6)、IronSource(5)、Unity(4)、穿山甲(3)、Vungle(2)、快手(1) | **TradPlus、Sigmob、Mintegral(Mbridge)、AppLovin、趣盟、风车Windmill** |

## E2. 结论

1. **"是否被完整收录"——否，且缺口巨大**：Thanox 禁用规则 89.5% 零覆盖、Fuck.AD 近半厂商零覆盖。LibChecker 的收录哲学是"识别锚点类"而非"全部可禁用组件"，天然不含大量推送/统计/欧美追踪 SDK 的组件。
2. **对 SDK-Slayer 的直接指导**：
   - 规则库**不能只靠 LibChecker 冷启动**——必须叠加 Exodus（补欧美签名级）+ Fuck.AD/AdClose hook 类名（补 TradPlus/Sigmob/Mintegral/AppLovin 等聚合 SDK）+ 自行从真实 APK 提取组件（补国产推送联盟）
   - LibChecker 部分（识别锚点 + 中英文描述 + 贡献者体系）可直接继承（Apache-2.0），这恰好是知识库的"骨架"；缺口部分是"血肉"
3. 缺口数据已量化存档：`research/coverage_gap_thanox_blocker_rules.json`（468 条完整对照）、`research/lcr_repo/`（LibChecker v44 全库本地副本）
