> 制定日期：2026-09-17 ｜ 状态：已成文，待用户批准后作为项目数据工作的统一准绳
> 背景：四轮调研 + 协议核查（含本轮两处新查实：Exodus 数据为 ODbL、AdClose 仓库无协议无源码）
> 关联：`research/2026-09-13_立项调研报告.md`（数据源全景）、HANDOVER.md §5（红线摘要）

## 1. 核心原则（五条）

1. **只用事实，不用表达**：组件名、包名、类名、SDK 归属关系是客观事实，不受版权保护；带创作性的表达（描述文案、数据库文件的组织结构、代码）不复制。我们从任何上游拿数据，重建进**自己的 schema**，描述文案自己写。
2. **不复制任何 GPL/AGPL/无协议项目的代码与数据库文件**（AppManager、Exodus 平台代码、Thanox 完整 JSON 原样搬运等）。客观事实可提取重建，载体不行。
3. **来源可追溯**：每条规则带 `source`（数据出处）与 `confidence`（置信度）字段，冷启动脚本产出的每条数据都能回答"从哪来"。这是自建库区别于竞品的关键资产，也是合规自证。
4. **协议分区**：我们的规则仓库主体 Apache-2.0；任何传染性协议（ODbL 同源共享等）的数据**不混入主体**，放独立目录并显式标注归属与协议（见 §3 Exodus 条目）。
5. **言行与口径一致**：规则库只陈述客观事实（识别特征、安全等级依据），文案中性，不预装"一键全网禁用"，与"SDK 组件审计/管理工具"的对外口径保持一致。

## 3. 是否自建库：结论是**建**，且必须建

1. **生态位空缺**（第四轮量化实证）：Thanox 468 条禁用规则 LCR 覆盖仅 6% 且锁死在 APK 内；"组件级 + 开源 + 活跃共建 + 安全禁用标注"四项交集没有任何项目占据。安全标注覆盖率（Thanox 39/468）是全行业最稀缺的数据。
2. **协议上没有捷径**：可直接继承的只有 LCR（识别锚点）+ oF2pks（31 条）——它们不含禁用知识；含禁用知识的源要么锁死（Thanox）、要么 ODbL 同源（Exodus）、要么禁商用（DDG）、要么无协议（AdClose）。**"安全禁用知识"这个核心资产只能自己积累**（实机提取 + 社区共建）。
3. **差异化立足点**：跨库合并层（以 SDK 实体为中心对齐多源特征 + 来源置信度）完全空白，自建库就是产品本身。

### 库的形态

- **独立仓库**（与 app 双仓，拍板已定），主体 **Apache-2.0** + NOTICE。
- **Schema**：Thanox general.json 实践范本扩展：`name / company / category / detect(包名前缀, 类签名, manifest特征) / components(四类组件模式) / safeToBlock / sideEffect / whitelist / source[] / confidence / contributors`。
- **ODbL 隔离区**：若冷启动要吃 Exodus 数据，放 `rules/exodus-odbl/` 独立目录，文件级 ODbL 声明 + 署名；主库条目以 `source: exodus` 引用其事实，不整体并入。是否启用该目录由 #3 冷启动脚本阶段决定，默认先不启用（LCR + Thanox 提取 + Fuck.AD + 实机提取已够首版 300+ 条的预期）。
- **消费方式两层**：
  - **构建期**：冷启动合并脚本（TODO #3）产出内置规则快照打进 app assets；
  - **运行期**：规则订阅（OkHttp 拉取版本化规则），用户可自建源——我们只维护官方源。

## 4. 调用上游数据的操作规范（给后续所有数据工作）

1. 新接入任何数据源前，先查协议并更新 §2 判定表；无协议 = 按 AdClose 模式（仅事实参考）处理。
2. 提取脚本与提取物落 `research/`，合并产物进规则仓库，全程留 `source` 痕迹。
3. 逆向只对本地已有的 APK 做（调研样本或用户自己设备导出），不批量抓取任何云端规则接口。
4. 不复制任何上游的描述文案——所有中文描述自己撰写（Thanox 的 description 也不抄）。
5. GPL/AGPL 项目的仓库可以读文档/读 issue 学思路，但不 fork、不下载其规则数据文件进项目目录。
