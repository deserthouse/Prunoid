# AdClose v4.3.2 拆解记录（2026-09-17）

> 来源：官方发布仓 Xposed-Modules-Repo/com.close.hook.ads（zhisynlim 仓库只是无源码镜像）
> 方法：pyaxmlparser manifest + dex 字符串扫描（脚本 research/extract_adclose_strings.py，产物 research/adclose_dex_strings.txt 30593 条）

## 核心结论：无内置 SDK 数据库，无可收割规则数据

1. **规则形态**：用户自定义 hook 规则 JSON（`custom_hooks_*.json` 导入导出）+ 用户手填 ruleUrl 订阅列表（`_request_list.json`，BlockListViewModel 有 addListUrl/removeList 等管理逻辑）。规则内容全部来自用户/社区分享的云端列表，APK 内零内置——与 AdHammer 同模式。
2. **规则字段**（dex 序列化字段名提取）：`appName / packageName / processName / className / methodName / status`——典型 hook 路线（类名+方法名），**非组件路线**，对我们只有"哪些 SDK 存在"的事实参考价值，规则结构不可平移（我们禁组件，它 hook 方法）。
3. **hook 入口函数**（R8 混淆后保留的可读名，量少）：blockAds / blockAdsWithPackageName / blockAdIdWithString / blockAdIdWithBaseBundle / blockAnyThinkNet / blockFirebaseWithString / blockGoolgeAdsInitialize / blockQueryUveAdRequest / blockReceiverRegistration（最后这个是"拦截 receiver 注册"的 hook 手法，与 IFW 目标等价但路线不同）。间接确认覆盖 AnyThink、Firebase、Google Ads 等 README 所列 SDK，但 dex 内无任何一家 SDK 的组件类名清单（混淆零散字符串不算数据）。
4. **项目状态修正**：调研报告写的 v4.2.2（2026-01）已过时——实际 2026-04-08 仍在更新（4.3.2）。"AdClose 停更"表述不成立，但其 GitHub 仓库无源码无协议的判定不变。

## 补充二：它怎么知道哪个 SDK 是广告 SDK（同日追加）

深挖 hook 包结构（`hook/ha/` 下 AutoHookAds / SDKAdsKit / AppAds / SmartFakeContext + 混淆类 a~o）与字符串分布，结论：**三条知识渠道，没有一条是静态规则库**：

1. **编译进代码的手工 hook 规则**：按 app/按 SDK 的 hook 逻辑在 R8 混淆类 `hook/ha/a~o` 内。目标 SDK 类名/方法名在 dex 明文字符串、resources.arsc 中**均零命中**（bytedance/qq/baidu/kwad/anythink 等 17 个前缀全部搜空）——目标串经字符串混淆/加密处理（dex 内可见大量装饰性垃圾长串，含 className/broadcast 等碎片）。这是 AdClose 的核心 IP，刻意防提取。
2. **运行时自动探测（AutoHookAds）**：集成 DexKit（LuckyPray，native 层），用 `nativeBatchFindMethodUsingStrings` / `findMethodsWithString` 等在**目标 app 自己的 dex 里**做字符串模式搜索 + `isValidSdkMethod` 启发式判定，找到广告 SDK 方法后 hook 并缓存（findAndCacheSdkMethods）；UI 有"自动探测"入口与 AutoDetectReceiver。**它不需要预先知道 SDK 清单——现查现学**。
3. **用户/社区自定义规则**：custom_hooks JSON（className+methodName）+ 订阅列表。

**对我们的启示**：AdClose 的路线证明"无需静态知识库也能定位广告 SDK"（DexKit 启发式现查），但其识别结果不可持久化共享、每次冷启动重查、不可审计——恰好反衬我们"可共建、可审计、可离线的静态知识库 + 端侧确定性匹配"路线的差异化。DexKit 启发式可作为我们扫描器 v2 的备选增强（MIT 协议，需单独评估）。

## 补充：默认云端订阅 URL 调查（同日追加）

- **结论：没有内置默认订阅 URL**。dex 中 ruleUrl 相关仅有占位符（`https://example.com/path/`、`https://nonexistent.com/path/N`，用于校验逻辑），无任何 raw.githubusercontent 等真实规则源；默认规则列表为空，全靠用户自填
- dex 内嵌的一组 GitHub 链接是"关于/推荐规则源"页面的社区仓库署名，非默认订阅：
  - 8680/GOODBYEADS、damengzhu/banad（手机去广告规则）
  - TG-Twilight/AWAvenue-Ads-Rule（秋风广告规则）
  - fmz200/wool_scripts（羊毛脚本）
  - sve1r/Rules-For-Quantumult-X（代理去广告规则）
  - 这些均为 hook 请求拦截类订阅源，与组件禁用路线无关
- **项目真实主仓为 zjyzip/AdClose**（2026-08 仍更新；zhisynlim 仓库为无源码镜像）。主仓 LICENSE = **CC BY-NC-SA 4.0**（禁商用），其代码本就不复用，此发现仅加固"零接触"判定
- 核心去广告能力（按 app 阻止 SDK 初始化/hook）是**编译进代码**的，不走订阅；订阅机制只服务于"网络广告请求拦截列表"
